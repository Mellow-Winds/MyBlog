# 1.中间计算过程中的整数溢出陷阱

将计算结果赋值给 `long long` 并不意味着计算过程就是安全的。如果操作数是`int`，溢出可能在赋值发生之前就已经发生。
### 1. 核心现象：赋值不改变运算环境
写下 `long long res = a * b * c;` 时，编译器并不是直接以 64 位精度计算。
**运算逻辑遵循以下步骤：**
1. **确定运算类型**：编译器查看操作数 `a` 和 `b` 的类型。如果都是 `int`，则该次乘法的临时结果类型也是 `int`。
2. **执行计算**：计算 `a * b`。如果结果超过了 `int` 的表示范围（约 $\pm 2.1 \times 10^9$），会发生**截断溢出**。
3. **继续运算**：用那个已经损坏的“残留值”继续乘以 `c`。
4. **类型提升（最后一步）**：将最终产生的 `int` 结果提升（Promote）为 `long long` 并存入 `res`。
**结论**：如果中间步骤溢出了，赋值给再大的变量也无法得到正确的结果。
### 2. 图解分析：32 位与 64 位的差异

| **场景**   | **计算表达式**                     | **编译器行为**                 | **结果状态**  |
| -------- | ----------------------------- | ------------------------- | --------- |
| **错误方案** | `res = a * b * c;`            | 在 32 位寄存器中计算，结果截断后转 64 位  | **溢出/错误** |
| **正确方案** | `res = (long long)a * b * c;` | 将 `a` 提升为 64 位，后续运算全部自动升级 | **正确**    |

### 3. 解决方案：强制类型提升
要确保整个运算链条都在 64 位环境下进行，必须**至少将其中一个操作数**显式转换为 64 位。
#### 方法 A：显式强制转换（推荐）
```c
// 只要第一个数是 long long，后续所有乘法都会按 long long 处理
res = (long long)a * b * c; 
```
#### 方法 B：预定义变量类型
```c
// 直接定义为 64 位类型
long long la = a;
res = la * b * c;
```
#### 方法 C：乘法因子预处理（常量场景）
```c
// 如果有常量参与，给常量加 LL 后缀
res = 1LL * a * b * c; 
```
