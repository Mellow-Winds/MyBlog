# 题干：Project 01 — REPL（Read-Eval-Print Loop）  
  
## 背景  
  
**REPL**（Read-Eval-Print Loop，读取-求值-打印循环）是一种经典的交互式编程环境，广泛用于 Lisp、Python、Ruby 等语言的命令行 Shell 中。它的工作方式非常直观：  
  
1. **Read**：读取用户输入的一行字符串  
2. **Eval**：对这个字符串进行求值（本次作业中直接原样返回）  
3. **Print**：将结果打印到控制台  
4. **Loop**：重复以上过程，直到用户输入 `exit`  
  
本次作业是整个 Lisp 解释器项目的起点。你只需要实现最基础的交互循环，后续作业将逐步为 `EVAL` 和 `READ` 添加真正的解析和求值能力。

### 行为描述  
  
程序启动后进入无限循环，每次循环：  
  
1. 从标准输入读取一行字符串  
2. 若读取到 `null`，跳过本次循环  
3. 若读取到 `"exit"`，退出循环，程序结束  
4. 否则，调用 `PRINT(RE(null, line))` 并用 `System.out.println` 输出结果  
  
若发生 `IOException`，打印错误信息后退出循环。  
  
### 示例  
  
```  
输入: hello  
输出: hello  
  
输入: (+ 1 2)  
输出: (+ 1 2)  
  
输入: exit  
（程序退出，无输出）  
```

# Answer
```java
public static void REPL() {  
    BufferedReader br = new BufferedReader(new InputStreamReader(System.in)); 
    //   1. 使用 BufferedReader + InputStreamReader 读取标准输入   
    try {  
        while (true) {  
            String line = br.readLine();  
            if (line == null) {  
                continue;  
            } else if (line.equals("exit")) {  
                break;  
            } else {  
                String res = PRINT(RE(null, line));  
                System.out.println(res);  
            }  
        }  
    }  
    //   2. 循环读取每一行：  
	//      - 若读取到 null，跳过（continue）  
	//      - 若读取到 "exit"，退出循环（break）  
	//      - 否则，调用 PRINT(RE(null, line)) 并用 System.out.println 输出结果  
    catch (IOException e){  
        System.out.println(e.getMessage());  
    }
    //   3. 捕获 IOException，打印错误信息后退出循环
}
```

# 笔记
## 1. 关于BufferedReader
### 1.1 只需写一次BufferdReader即可实现一直读取
我最早写的是：
```java
while(true){  
   BufferedReader br = new BufferedReader(...)  
}
```

这是没有必要的。这样的话，每次循环都会创建对象。但是输入流本来就是持续的，`System.in`是一个流。只需要创建一次，就可以读取多次。
正确结构：
```java
BufferedReader br = new BufferedReader(...)  
  
while(true){  
   br.readLine()  
}
```

### 1.2 BufferedReader如何使用
首先是一个基础的
```java
BufferedReader br = new BufferedReader(new InputStreamReader(System.in)); 
```
通过 `BufferedReader` 建立一个**缓冲区**（默认 8KB），它会预先从数据源批量读取大量字节存入内存
当调用 `readLine()` 时，它直接从内存缓存中取数据。
```java
String line = br.readLine();  
```
这行代码实际上涉及了三个对象的嵌套：

| **层次** | **组件**              | **作用**                          | **类比**                    |
| ------ | ------------------- | ------------------------------- | ------------------------- |
| **底层** | `System.in`         | 标准输入流（字节流），负责接收原始二进制数据。         | 像是一根**吸管**，一次只能吸一滴水。      |
| **中层** | `InputStreamReader` | **桥梁流**，负责将字节（Byte）解码为字符（Char）。 | 像是**转换头**，把水滴变成可以理解的字符。   |
| **顶层** | `BufferedReader`    | **缓冲流**，负责提供缓冲区并支持按行读取。         | 像是**蓄水桶**，先把水接满，让你一口气喝个够。 |
BufferedReader 是类吗？
**是的，是一个类。**
它位于 `java.io` 包下，继承自 `Reader` 抽象类。它的构造函数要求传入另一个 `Reader` 对象，这也就是为什么我们需要先用 `InputStreamReader` 把 `System.in` 包装一下的原因。

下面的是AI给出的代码，应该是比较完备的代码块。
### 1. 代码骨架与对应含义
我们先看完整的经典结构，随后进行逐块（Block）拆解：
```java
try {
    // 1. 监控区：假设下面这行代码抛出了异常
    dangerOperation(); 
    // 2. 紧跟在异常后的代码（这行将永远不会被执行）
    safeOperation();   
} catch (SpecificException e) {
    // 3. 捕获与恢复区
    log.error(e);      
} finally {
    // 4. 绝对执行区
    cleanupResources(); 
}
```

### 2. 逐行级逻辑拆解

#### **区块 A：`try` 块（监控沙箱）**
- **含义：** 这是一个隔离沙箱。程序在这里执行具有潜在风险的操作。
- **`dangerOperation();` 是什么？**
    - 它代表**任何声明了可能抛出异常的方法**。（说白了就是指代这里的所有操作代码。）
    - **在的 REPL 项目中：** 它对应的就是 `String line = br.readLine();`。读取输入流是一个“高危动作”，因为物理设备可能随时断开连接。
- **控制流阻断特性：** 一旦 `dangerOperation()` 触发了异常，`try` 块内部剩余的所有代码（如 `safeOperation()`）将被**立刻物理截断**，不再执行。程序的执行指针会直接“跳跃”到匹配的 `catch` 块。

- **大概意思就是：程序在`try`中需要尝试ABC三步，可能AB是出现问题的`dangerOperation();`，C是不会出问题的`safeOperation(); `。那么一旦发现A或B出现问题，就停止工作，不再进行C代码。**
#### **区块 B：`catch` 块（异常拦截器）**
- **含义：** 异常的“捕网”。你可以根据不同的错误类型设定不同的拦截策略。
- **`SpecificException` 是什么？**
    - 这是你要拦截的**具体异常类型**。异常在 Java 中有着严格的分类层级。
    - **在这个的 REPL 项目中：** 它对应 `IOException`。这意味着这个拦截器只抓取输入/输出相关的物理错误（比如流断开），如果发生了 `NullPointerException`（空指针），它是不管的，程序依然会崩溃。
- **`e` 是什么？**
    - 它是被抓获的那个**异常对象（实例）**。它封装了崩溃瞬间的所有现场信息。
- **`log.error(e);` 是什么？**
    - 它代表**异常发生后的止损与恢复操作**。（说白了也是一个象征性的伪代码）
    - **在你的 REPL 项目中：** 它对应 `System.out.println(e.getMessage());`。你可以通过调用 `e.getMessage()` 提取错误原因，或者通过 `e.printStackTrace()` 打印完整的崩溃调用栈（Stack Trace），以便进行战略复盘。
#### **区块 C：`finally` 块（绝对防线）**
- **含义：** 收尾清理区。它是 Java 异常处理中最具有“契约精神”的设计。
- **执行特性（极度重要）：** 无论 `try` 块中的代码是完美运行，还是中途崩溃跳入 `catch`，甚至你在 `try` 块里写了 `return` 语句试图提前退出方法，**`finally` 块中的代码都拥有最高优先级的绝对执行权**（除非运行该程序的物理机断电或 JVM 进程被强制杀掉）。
- **`cleanupResources();` 是什么？**
    - 它代表**释放底层系统资源的动作**。
    - **在 REPL 项目中（如果使用老版本写法）：** 应当在这里写入 `br.close();`。因为无论读取是否报错，之前向操作系统申请的“输入流句柄”必须归还，否则会导致内存与句柄的永久泄露。
### 3. 现代 Java 推荐 Try-with-Resources
理解了上述经典模型，就能明白为什么我们在上一阶段推荐 Java 7 引入的 **Try-with-Resources (TWR)** 语法：
因为 `finally` 块中的 `br.close();` 本身也是一个 `dangerOperation`，它也有可能抛出异常！如果按照经典模型手写，你必须在 `finally` 里面再嵌套一层 `try-catch`，导致代码逻辑极度冗余且不具备美感。
TWR 语法（将资源初始化放在 `try(...)` 的括号中）正是由编译器在底层自动帮你生成了完美且严密的 `finally` 释放逻辑，实现了“低成本避错”。
